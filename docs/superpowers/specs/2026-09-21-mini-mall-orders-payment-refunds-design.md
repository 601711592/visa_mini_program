# 小程序商城订单、微信支付与退款设计

日期：2026-09-21

## 目标与已确认范围

让现有 uni-app 商城从内存演示订单转为真实交易：会员可结算、查看订单、使用积分及优惠券、微信支付、申请整单退款；商家在现有管理后台配置优惠、审核退款，并在现有签证订单体系办理和处理物流。两个小程序的会员、订单、资产及商户号相互隔离。每个可下单商品必须配置签证类型；一次结算的每条商品明细在支付成功后生成一笔现有体系的办理单。

本设计依据 `docs/mall-iteration/README.md`、`REQUIREMENTS.md`、`LOGIN.md` 及已确认的商城页面。原型中的折扣、积分上限、券门槛和期限不是正式规则；这些值在后台按小程序配置并启用后才参与真实交易。现有商城页面的布局和游客浏览路径继续沿用。

## 方案与系统边界

采用独立的小程序交易订单作为收款、优惠、退款及会员资产的主记录。旧 `order` 表保留为签证办理记录，通过明细关联表与小程序订单相连。这样避免旧订单的单商品、店铺状态和线下付款语义承担购物车与微信交易。小程序、Laravel 后端和管理后台分别改造，不建立第二套办理进度引擎。

后端新增小程序订单主表、订单明细、出行人快照、支付尝试、退款申请、会员积分账户与不可变流水、优惠券模板和会员券、按小程序的交易规则、库存占用及履约关联。金额统一使用整数分，积分使用整数。订单和每条明细保存商品、套餐、人群、日期、价格、规则版本及地址快照；出行人护照等完整资料加密存储，仅向会员和后台授权场景提供必要字段，小程序普通订单详情展示脱敏护照号。后台商品配置增加签证类型映射和是否必须填写出行人。

小程序订单只允许当前登录会员读取或操作；后台交易接口走现有后台鉴权与独立权限。每次读写都以会员会话中的 `mini_program_id` 为准，不信任客户端传来的归属字段。商户私钥、API v3 密钥和平台验签材料仅在服务端安全配置中保存，按小程序映射，不返回管理后台或小程序。

## 结算、计价与资产

购物车可继续保存在客户端，结算时只上传商品 ID、稳定的套餐 key、人群、日期、数量、对应出行人及所选券和积分意向。服务端报价接口逐项验证上架状态、小程序归属、签证类型、套餐和人群、日历价格、购买上限和库存。日期／人群名额未明确配置或不足时不可下单；服务端维护占用数，待付款取消或到期时释放，支付成功后转已售。前端传来的单价、折扣和实付均不参与计算。

管理后台按小程序配置多人优惠的范围、门槛、折扣和有效期，优惠券模板的适用商品、门槛、面额及有效期，积分抵扣上限、赠分基数、优惠叠加次序、支付时限和在线退款期限。规则缺失时对应优惠不可选；支付时限缺失时禁止创建可支付订单。单笔订单至多一张券，允许与积分叠加。积分兑换比例为已确认的 500 积分抵 10 元，永久有效；交易完成后每消费 1 元得 1 积分，零头四舍五入，赠分基数采用后台已启用配置。首次验证绑定手机号对应 10 元新人券资格，发券以会员为幂等键；券模板有效期和门槛未配置前只保留待发资格。

报价返回逐项金额、权益适用性、规则版本和过期时间。提交时在事务内重新计算、锁定库存与会员资产，校验报价版本；变化时返回新报价并要求用户重新确认。创建订单使用会员范围内唯一幂等键，防止重复提交。积分和券在待付款阶段占用，取消或支付超时后释放；支付成功后记为已使用。积分奖励仅在所有关联办理单达到完成状态后记一次。退款成功后按后台规则返还已用积分、券并处理已赠积分，所有变动记录可追溯流水；退款申请或网关受理时不提前返还。

## 支付、取消与退款状态

两个小程序分别使用已绑定的普通微信商户号。会员发起付款时，服务端核对订单归属与待付款状态，调用微信支付 API v3 小程序下单，返回 `wx.requestPayment` 所需签名参数。重复付款沿用同一商户订单号，在预支付凭据过期时重新获取。小程序支付回调只触发服务端查单与页面刷新；订单支付成功必须由经过验签、解密及商户号、AppID、订单号、金额核对的微信通知或主动查单结果确认。支付通知可重复送达，状态转换必须幂等。[微信支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791870)、[小程序调起支付](https://pay.wechatpay.cn/doc/v3/merchant/4012791898)。

待付款取消或到期处理先向微信查单；确认未支付后关单，再将本地订单置为已取消并释放库存和权益。若查得已支付，则按支付成功处理，避免取消与回调竞态。查单补偿任务处理漏通知、超时和未知状态；后台可查看异常并发起受控重查。付款状态分为待付款、支付确认中、办理中、已完成、已取消；退款申请、审核中、退款处理中、已退款和驳回原因单独保存，避免混淆办理状态。

会员可在后台配置的期限内提交整单退款申请，期限从支付成功时起算且不超过微信支持的期限。后台人员审核通过后立即暂停关联办理单，并以固定、唯一的商户退款单号发起微信原路退款；重复提交与重试使用同一退款单号。微信受理只进入退款处理中；验签、解密后的退款通知或主动退款查询确认成功后，才转已退款、返还资产并永久终止办理。审核拒绝保留原因，订单仍可正常办理；退款失败进入可重试或人工处理状态，不能伪装成功。[微信退款申请说明](https://pay.wechatpay.cn/doc/v3/merchant/4012791862)、[退款结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4012791906)。

## 履约与管理后台

支付成功后提交可重试的履约任务：每条小程序订单明细生成一笔旧体系办理单，并关联其签证类型、会员客户、出行人、地址及原交易订单号。同一明细只允许生成一次；失败保留已收款交易和明确异常状态供后台处理，不重复收款。每个小程序配置专属后台店铺和新的“小程序”店铺类型；该类型复用现有签证办理能力，但不继承线下订单的人工付款确认与删除权限。会员按小程序建立稳定的后台客户映射，避免每笔交易重复建客户。旧办理单进度和物流回写或投影到小程序订单详情；全部办理单完成后，交易主单完成并触发赠分。退款失败时由后台决定是否恢复已暂停的办理单，操作留痕。

管理后台增加小程序订单列表与详情、支付和履约异常、退款审核与结果、按小程序的交易规则、优惠券模板及会员资产管理；商品编辑增加签证类型和出行人要求。退款审核与资产调整需要独立权限和操作日志。现有旧订单页面通过关联号可跳到交易主单，避免工作人员将旧线下“支付确认”误用于微信订单。

小程序保留现有购物车、结算、订单、支付及退款页面，替换 `src/store/mall.ts`、`src/store/center.ts` 的模拟订单和资产来源。结算显示服务端报价、规则变化及库存不足反馈；支付页显示真实支付、取消、失败和确认中状态；订单列表及详情支持加载、空数据、错误重试、状态刷新。登录恢复保留非敏感商品选择，恢复后仍需用户主动提交或支付。

## 验收与上线条件

后端以网关模拟器测试报价防篡改、跨小程序及跨会员隔离、名额和权益并发占用、重复提交、重复与乱序支付通知、取消和支付竞态、重复退款、退款失败和成功后资产返还、办理单重试不重复。前端验证多商品及同商品不同规格出行人归属、价格变化重新确认、登录恢复和真实状态展示，并执行类型检查及两个微信目标构建。管理后台验证权限、按小程序配置与审核日志。

上线前配置并核对两个真实 AppID 与商户号绑定、各自 API v3 凭据、HTTPS 通知地址、正式优惠规则和商品签证类型；执行数据库迁移与受控的小额真机支付、取消、退款及对账。仓库当前 `app1`／`app2` 的 AppID 配置仍相同，必须在联调时核实真实映射。未取得商户配置时可以完成代码和模拟网关验证，但不能宣称真实资金链路已验收。

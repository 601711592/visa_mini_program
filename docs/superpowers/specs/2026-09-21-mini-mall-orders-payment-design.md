# 小程序商城订单与微信支付设计

日期：2026-09-21

## 目标与范围

让现有 uni-app 商城的“立即购买 → 确认订单 → 微信支付 → 我的订单”从内存演示转为真实交易。会员可按商品套餐、人群、日期和人数下单，填写对应出行人、选择邮寄地址（必填）、使用积分及优惠券，并查询、取消及继续支付自己的订单。商家在现有管理后台配置优惠，付款后按商品明细生成现有体系的办理单，继续使用现有订单管理和签证管理页面办理。两个小程序的会员、订单、资产及普通微信支付商户号相互隔离。

本轮只从商品详情的“立即购买”进入真实结算，真实订单 API 暂只接受一条商品明细；数据结构保留明细表，后续购物车接入时可扩展多明细。已有演示购物车入口和从购物车结算的真实交易入口在本轮隐藏，避免模拟金额进入真实支付。退款、文档外新需求“填表打通”、小程序端签证节点与物流进度展示延后。现有结算页的出行人填写、逐商品校验仍在本轮范围内。

本设计依据 `docs/mall-iteration/README.md`、`REQUIREMENTS.md`、`LOGIN.md` 及已确认的商城页面。原型中的多人折扣、积分上限、券门槛和期限是演示值，不直接作为正式规则。

## 方案与数据边界

建立独立的小程序交易主单，负责服务端计价、支付、会员资产和订单展示。主单记录会员、小程序、订单号、状态、金额（整数分）、规则版本、地址快照、支付时限及幂等键；商品明细记录商品、稳定套餐 key、人群、日期、数量、单价和签证类型快照；出行人按明细关联。护照等完整资料在服务端加密保存，小程序订单详情只返回必要的脱敏信息。旧 `order` 表继续负责办理，不承担微信支付与优惠计算；关联表保存每条商品明细对应的旧办理单号。

每个可下单商品在管理后台配置必填签证类型和是否需要出行人。服务端拒绝签证类型缺失、失效或与商品小程序归属不符的交易。小程序 API 只允许当前登录会员访问自己的订单；后台接口使用现有管理员鉴权和独立权限。所有读写以会员会话内的 `mini_program_id` 为准，不信任客户端传入的归属字段。

## 结算、优惠与库存

立即购买携带商品 ID、套餐 key、人群、日期、数量和本明细出行人进入结算。服务端报价逐项核对上架状态、小程序归属、签证类型、套餐、人群、日历价格、购买上限和可售名额。日期／人群名额未配置或不足时不可下单；服务端记录待付款占用，取消或到期释放，付款成功转已售。客户端传来的单价、折扣、实付不参与计价。

管理后台按小程序配置多人优惠范围、门槛、折扣和有效期，优惠券模板适用商品、门槛、面额及期限，以及积分抵扣上限、赠分基数、优惠叠加次序和支付时限。未启用的优惠不可选择；未配置支付时限时禁止创建可支付订单。单笔订单至多一张券，可与积分叠加。已确认的积分比例是 500 积分抵 10 元、永久有效；交易完成后每消费 1 元得 1 积分，零头四舍五入，赠分基数由已启用的后台规则指定。首次验证绑定手机号产生 10 元新人券资格，按会员幂等发放；券模板门槛和期限未配置时保留待发资格。

报价返回分项金额、权益适用性、规则版本及有效时间。提交时要求选择当前会员名下的有效邮寄地址；服务端读取地址并保存完整快照，缺失、已删除或跨会员地址均拒绝提交。在数据库事务内重新报价并锁定库存、积分和券；金额或资格变化时返回新报价，由用户重新确认。会员范围内唯一幂等键防止重复下单。积分和券在待付款时占用，取消或支付到期后释放，支付成功后记为已使用。全部关联办理单完成后发放一次消费积分；后台资产调整保留流水和操作日志。

## 微信支付、取消与订单状态

两个小程序各自关联普通微信商户号。服务端按小程序选择商户号、AppID、商户私钥、API v3 密钥及验签材料；密钥只存在服务端安全配置中，不返回小程序或管理后台。会员发起付款时，服务端核对订单归属和待付款状态，调用微信支付 API v3 小程序下单，返回 `wx.requestPayment` 所需参数。继续付款使用同一商户订单号，预支付凭据过期时重新获取。[微信支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791870)、[小程序调起支付](https://pay.wechatpay.cn/doc/v3/merchant/4012791898)。

小程序支付回调只触发服务端查单和页面刷新。订单付款成功必须由验签、解密并核对商户号、AppID、订单号和金额的微信通知或主动查单结果确认；重复通知与重复查单不得重复扣权益或生成办理单。待付款取消、支付到期时先向微信查单，确认未付款后关单，才释放名额、券和积分；若已付款则转入成功处理。后台补偿任务处理漏通知、超时和未知状态，并提供受控重查入口。

主单状态为待付款、支付确认中、已付款待建单、办理中、已完成、已取消。支付失败或用户关闭收银台后仍可在支付期限内继续付款。退款入口与退款状态本轮不出现在小程序或管理后台；后续退款模块须以微信最终退款结果为准并补充资产返还。

## 现有后台订单与签证管理衔接

付款成功后提交可重试的履约任务：当前每笔交易的一条商品明细生成一笔旧 `order` 办理单，并写入签证类型、国家、会员对应客户、联系人、金额及下单时的邮寄地址快照。商品要求填写出行人时，逐人生成 `order_visa` 记录，人数与办理单一致；商品配置免填时，办理单保留购买人数，由后台补录签证记录。明细到旧订单号建立唯一约束，任务失败可重试但不能重复建单或再次收款。

每个小程序配置专属后台店铺和新的“小程序”店铺类型。该类型复用线下签证列表、添加与状态处理能力，但不得继承线下订单的人工确认付款或删除权限。现有线下建单依赖后台登录操作人和客户数据，支付回调不能直接调用该建单入口；履约服务需独立构建所需快照，并按会员和小程序建立稳定客户映射。后台订单列表标明小程序来源，并能从交易主单跳到旧办理单及签证管理。

本轮现有后台签证管理可操作小程序办理单。交易订单的“已完成”判定和赠分由后端读取关联办理单中所有签证记录的现有完成终态；尚未补录签证记录的办理单不能自动视为完成。小程序仅显示汇总订单状态，不展示签证节点、申请材料流转或物流详情。办理单生成失败时，已收款交易仍可在后台订单异常列表查看并重试，会员端显示“已付款，正在安排”，不显示虚假的“办理中”。

## 页面改造与验收

小程序沿用商品详情、确认订单、出行人、支付、订单列表和详情的既有布局，把 `src/store/mall.ts`、`src/store/center.ts` 中模拟订单、支付和资产来源替换为真实接口。商品详情保留“立即购买”，隐藏购物车入口与加购按钮；订单页隐藏申请退款按钮，移除“模拟支付成功／取消／失败”按钮。结算页优先展示默认邮寄地址，没有地址时引导新增；地址为必填，未选择时阻止提交并给出明确提示。结算展示服务端报价、规则变化和库存不足反馈；支付页展示真实支付、取消、失败与确认中状态；订单页支持加载、空数据、错误重试和状态刷新。登录恢复保留所选商品和出行人草稿，恢复后仍由用户主动提交或支付。

后端使用网关模拟器验证报价防篡改、会员与小程序隔离、缺失／已删除／跨会员邮寄地址拒单、库存及权益并发占用、重复下单、重复和乱序支付通知、取消与付款竞态，以及履约任务重试不重复建单。小程序验证直接购买、地址必填与新增返回、出行人归属、价格变化重新确认、登录恢复和真实状态展示，并执行类型检查及两个微信目标构建。管理后台验证商品签证类型、规则配置、权限、办理单与签证记录生成。需要用真实商户凭据完成微信开发者工具和真机受控小额付款、取消及对账，才能认定资金链路联调完成。

上线前核对两个真实 AppID 和各自商户号绑定、API v3 凭据、HTTPS 通知地址、正式优惠规则、支付时限及商品签证类型，并执行数据库迁移。仓库当前 `app1`／`app2` 的 AppID 配置仍相同，联调前必须核实真实映射。没有商户配置时可完成代码和模拟网关验证，但不能宣称真实资金链路已验收。
